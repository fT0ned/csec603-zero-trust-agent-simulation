# GitHub secret scanning eligibility and remaining requirement

Checked October 23, 2026, Asia/Dubai, using authenticated GitHub REST reads and the repository owner's authenticated browser settings. The governing project document requires enabling GitHub secret scanning. That requirement remains unmet for the current private, user-owned repository.

The REST repository response returned HTTP 200, private visibility, owner type `User`, and administrator permission. The `security_and_analysis` field was absent; its absence alone was not treated as proof of either feature state or eligibility. The dedicated secret-scanning alerts endpoint returned HTTP 404 with the message “Secret scanning is disabled on this repository.” No alert contents or authentication credentials were preserved.

The authenticated [Advanced Security settings page](https://github.com/fT0ned/csec603-zero-trust-agent-simulation/settings/security_analysis) offered only Dependency Scanning and Dependabot controls. It contained no Secret Protection section, secret-scanning enable control, or push-protection enable control. The complete observed page text and a screenshot are preserved in `github-secret-scanning-settings-dom.txt` and `github-secret-scanning-settings.png`; `github-secret-scanning.json` records their hashes and the API observations.

GitHub's [secret-scanning eligibility documentation](https://docs.github.com/en/code-security/how-tos/secure-your-secrets/detect-secret-leaks/enable-secret-scanning) makes secret scanning free for public repositories and available for organization-owned private repositories with the relevant Secret Protection entitlement. Its user-owned repository support is restricted to the documented enterprise-managed cases. The current private repository's owner settings do not offer that feature. This is a repository ownership/feature-eligibility blocker, not merely an unknown setting or a lack of administrator permission. The API did not disclose an account plan, so no specific account subscription is claimed here.

No purchase, upgrade, paid product enablement, repository transfer, or visibility change was attempted. No settings were changed. A private-repository product enablement request was not used as a speculative entitlement probe because it could create a paid commitment. GitHub's [Advanced Security documentation](https://docs.github.com/en/get-started/learning-about-github/about-github-advanced-security) identifies the applicable private-repository products and plans.

## Exact unblock steps

1. The owner must identify an eligible organization or enterprise repository location with an existing GitHub Secret Protection entitlement that covers this repository without additional charges. If none exists, a hosting/entitlement change requires a separate owner decision and any necessary billing authorization. Purchasing a license was not authorized for this work.
2. If the owner chooses a transfer into such an organization, explicitly authorize the ownership/access change, keep the repository private, and update the remote URL and paper/reproduction links afterward. The implementation did not make this change because it would alter the specified private repository's ownership and access context.
3. In the eligible repository, open Settings → Advanced Security. Review the Secret Protection impact and confirm that enablement is covered by the existing entitlement before enabling it. Then enable secret scanning and [push protection](https://docs.github.com/en/code-security/how-tos/secure-your-secrets/prevent-future-leaks/enable-push-protection).
4. Re-read the repository API and confirm `security_and_analysis.secret_scanning.status` and `security_and_analysis.secret_scanning_push_protection.status` are both `enabled`. Confirm the alerts endpoint is accessible, preserve a fresh owner-settings screenshot, and update the requirement status in this evidence record.

The repository's local staged-secret scanner remains a separate defense. It does not satisfy or replace the required GitHub-hosted secret-scanning feature. This external setting does not change the recorded experimental outcomes, but must remain an explicit handoff blocker until the owner resolves eligibility and verifies enablement.
