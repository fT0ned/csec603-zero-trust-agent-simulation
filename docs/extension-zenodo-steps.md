# Publish the extension DOI

The study002 release is [extension-study-002](https://github.com/fT0ned/csec603-zero-trust-agent-simulation/releases/tag/extension-study-002); its public download/tag verification receipt is `docs/extension-study-002-release-verification.json`. The earlier [study001 release](https://github.com/fT0ned/csec603-zero-trust-agent-simulation/releases/tag/extension-study-001) stays unchanged. A DOI is not invented, and account login/author and license confirmation remain with the repository owner. `.zenodo.json` and `CITATION.cff` now describe study002 and use the public owner handle `fT0ned`; replace it with the intended publication creator names if appropriate. The original repo has no LICENSE file; no license for historical contributors' material has been invented in this task. Verify the intended deposit license before publication. Do not claim a DOI until its published record resolves.

## GitHub-linked route

1. Open [Zenodo login](https://zenodo.org/login/) and sign in with the GitHub account that owns the repository. Complete GitHub authorization if prompted.
2. Open the profile menu, select **GitHub**, click **Sync now**, locate `fT0ned/csec603-zero-trust-agent-simulation`, and enable its switch. If the repo is absent, grant Zenodo access in GitHub's application permissions and sync the Zenodo repository list again.
3. In the repository's Zenodo view, select **Create release**, then create/publish a GitHub release from the study002 archive commit recorded in the receipt above. If `extension-study-002` was published before linking, use a new archival release tag pointing at that same commit (for example `extension-study-002-doi`); do not move `extension-study-002-freeze-v1`, `extension-study-freeze-v1`, or either published archive tag, and do not rerun experiments for a DOI.
4. Wait for processing in Zenodo's GitHub view, then click the record DOI. If processing fails, open the failed release and expand **Errors**. Review creator metadata, version, software type, license, file list and source commit before relying on the deposit.
5. On the record page, verify the DOI resolves, the experimental config/freeze and results are present, and **External resources → Archived in** shows archival status. Record the DOI in `CITATION.cff` and the completion report as a later metadata-only commit.

## Manual route for the already published release

If the release predates enabling GitHub integration, download `extension-study-002.zip` and `SHA256SUMS` from the study002 release. Verify with `Get-FileHash .\extension-study-002.zip -Algorithm SHA256` against the release checksum/receipt. In Zenodo select **My dashboard → New upload** (or **New record**), upload that ZIP, choose resource type **Software**, set version **extension-study-002**, title/creators from `.zenodo.json`, the intended license, repository/release related links, and the description referring to this completion report. Select **Save**, **Preview**, then **Publish** after reviewing the deposited files and metadata. Copy the published version DOI (and distinguish its concept DOI if shown), verify it resolves, and add it to `CITATION.cff` and a metadata-only report update. Do not upload `.env`, `.runtime`, provider credentials, model weights or private signing keys.

Official guides consulted 2026-11-17: [enable a repository](https://help.zenodo.org/docs/github/enable-repository/), [archive a GitHub release](https://help.zenodo.org/docs/github/archive-software/github-upload/). The DOI is complete only after a published, resolvable Zenodo record exists; a GitHub tag or prepared metadata alone is not a minted DOI.
