# Deployed architecture and paper figure

[Fig. 1 SVG](figures/deployed-architecture.svg) supplies the vector paper layout. [The editable Mermaid topology](figures/deployed-architecture.mmd) preserves the same functional roles and trust boundaries for subsequent editing. The SVG was rendered and visually inspected; it is authors' work and describes the implemented single-machine C2 testbed.

Suggested caption: **Fig. 1. Deployed identity, delegation, decision/enforcement and independent evidence paths in the C2 testbed (authors' work).** Identity issuance and trusted principal delegation follow different paths. A genuine agent can receive injected content, while a separate client can replay its copied bearer credential. Host-only ground truth, checkpoints and committed tool-state reads support evaluation outside the system's audit claims.

The physical tool request path is `agent-client/attacker → gateway → PA → tool service`, with results returned through PA and gateway. OPA is the Policy Engine and supplies C2 allow/deny/approval decisions to the Policy Administrator. The PA reads trusted delegation and atomic workflow state, applies approval and one-use expiring JIT, and serializes the permitted tool effect. The gateway is the front Policy Enforcement Point: every condition validates credentials, checks the shared gateway deny-list and records the actual socket peer. The implementation places serialized tool-side enforcement inside the PA, so the figure deliberately does not invent a direct gateway-to-tools connection.

The LLM planning loop runs in the trusted host harness and calls the real provider API with mock enterprise content. The attested workload is the request-client container under UID 10001. SPIRE uses join-token node attestation and Unix UID workload selection to issue JWT-SVIDs through its workload API socket; the trusted harness fetches them using that client and supplies the disposable credential on stdin for requests. The provider receives no credential. A stolen bearer copy can still be replayed by the UID 10002 attacker client until expiry or revocation; issuance attestation is not token binding.

Principal, task scope, expected intent and delegation lineage enter the PA through its authenticated control interface. They are not taken from model-supplied tool parameters. The careful approver and rubber-stamp ablation are simulated rules, not a human study. Workflow counters and JIT consumption are serialized with the permitted tool action. C0 and C1 omit OPA/task/workflow/approval controls while retaining the same credential-validation and gateway deny-list mechanisms. C2-noWF and C2-RS change only the specified workflow or approval control.

Compose isolates the `control`, `identity` and `tools` networks internally. `agent-client` and `attacker` join only `front`; only the agent client mounts the workload socket. The PA joins `control`, `tools` and `admin`; the gateway joins `front` and `control`. The files, email, CRM and payment services have no published ports. Host loopback publishes gateway port 8766 and authenticated PA port 8767. No agent/attacker container mounts the Docker socket or host evidence folders.

The PA maintains the append-only service audit, and the host captures each observed audit response, verifies its next hash/sequence, and recomputes a separate count/hash checkpoint. The host writes ground-truth labels separately from the predictor's condition-visible input. Independent outcome collection uses trusted host Docker execution to call each tool's local `/evidence/{run_id}` endpoint and read committed state/write IDs. This is a diagnostic host privilege, not a client bypass path. The independent oracle protects against accepting the gateway's self-reported result as the sole success measure; it does not model control-plane compromise.
